# Проверка проекта перед защитой

**19 ноября 2026 года.** Все шесть пунктов задания участника 2 продемонстрированы в локальной сборке. Запуск из установленного пакета исправлен. Командный проект остаётся учебным прототипом. Два главных незакрытых требования относятся к защищённой пороговой подписи и к проверкам в сквозном сценарии безопасности.

## Проверка исправлений в следующей ветке

Первоначальная сверка ниже описывает снимок 6efd833. В следующей версии пороговая BLS-подпись объединяет проверенные вклады спутников. Дилер раздаёт независимый ключ каждой группе. Получатель сверяет доли с обязательствами Feldman, принимает пакет AES-GCM один раз и сохраняет состояние при смене узла. Обновление добавляет проверяемый полином с нулевым свободным членом. Для воспроизведения откройте отчёт из команды запуска в корневом README. Для просмотра текущего состояния ориентируйтесь на этот раздел и на тесты.

### О чём говорить на защите

1. Покажите один пакет на двух соседних минутах. Спутники 8, 69 и 70 образуют группу из трёх узлов. Отход спутника 70 сохраняет возможность чтения для Блэкли и Шамира при k=2. При XOR или CRT получение пакета откладывается. Открытый текст возвращается только после проверки тега AES-GCM.
2. Для количественного сравнения сначала зафиксируйте порог. При требовании «все шестеро» сравнение времени между всеми реализациями справедливо по отношению к доступности. При 3 из 6 возникает иной компромисс. Три отсутствующих узла допустимы, но трёх прочитанных подлинных долей уже достаточно для восстановления.
3. Различайте измерения и выводы модели. Время получено на этом компьютере. Число байтов рассчитано по заданному двоичному формату. Условие m ≥ t следует из порогового свойства при пассивном чтении долей. Для рандомизированного CRT до порога доказана статистическая оценка. Отказ функции принимать неполный набор сам по себе криптографической гарантии не даёт.
